# AGENTS.md

Instructions for coding agents (Claude Code, Codex and others). Humans: see [CONTRIBUTING.md](CONTRIBUTING.md). Operators and local setup: see [README.md](README.md). Follow these rules from the first prompt.

## Project

Vereinsbote is an open-source web app a club uses to send e-mails to its members and partners. The interface is German (default) and English. One instance serves one club, and it runs on Vercel, Cloudflare Workers or Node/Docker.

- **Spec:** `docs/superpowers/specs/2026-11-23-vereinsbote-design.md`; each sub-plan may add a design next to it (`…-02-kontakte-design.md`), which wins where it differs.
- **Roadmap** (eight sub-plans, written one after the other): `docs/superpowers/plans/2026-11-23-vereinsbote-00-fahrplan.md`
- **Plans:** `docs/superpowers/plans/` (currently `…-01-fundament.md`, `…-02-kontakte.md` and `…-03-gestaltung.md`; sub-plan 3 is split into 3a, the foundation, and 3b, templates and editor). The spec and the plans are in German; their "Global Constraints" are summarized below.

Access levels are cumulative (`read` < `edit` < `send`). The admin role gives no area access. There are no passwords and no self-registration: admins invite users.

## Stack and toolchain

- **Vite+ is the only toolchain** (`vite-plus`, CLI `vp`): `vp dev`, `vp build`, `vp check` (format, lint, types), `vp fmt`, `vp lint`, `vp test`, `vp run …`.
  - Configure only in `vite.config.ts`: the `fmt`, `lint`, `staged` and `test` blocks are in the root file, the app's plugins in `apps/web/vite.config.ts`.
  - Do not add `vitest.config.ts`, `oxlint.config.ts`, `.oxlintrc.json`, `.oxfmtrc.json`, Husky or lefthook.
  - Tests import from `vite-plus/test`, Vite APIs from `vite-plus` (lint rule `vite-plus/prefer-vite-plus-imports`).
- **pnpm 12** with `catalogMode: strict` in `pnpm-workspace.yaml`.
  - Every external dependency is `"catalog:"` in every `package.json`. Versions live only in the catalog.
  - Run `pnpm check:catalog` and `pnpm check:vite-plus` after touching dependencies. The Vite+ versions (`vite-plus`, `vite`, `vitest`, `@vitest/coverage-v8`) move together.
- **Always the newest stable version** of Node (26, see `.node-version`), pnpm, TypeScript, every dependency and every image. An older version needs a proven reason, written as a comment at the catalog entry.
- Mail and images: `@react-email/render` and React render the mails, `simple-icons` (CC0, dev only) is the source of the social icons, `s3mini` (S3), `@vercel/blob` and the R2 binding are the image storages. Images are processed in the browser with the platform's own APIs.
- App: TanStack Start, React, React Aria Components (dates through `@internationalized/date`), Tailwind CSS v4, Drizzle ORM, Better Auth, zod. Import files: `read-excel-file` (XLSX), `papaparse` (CSV) and `fflate`, which unzips XLSX synchronously because its asynchronous unzip starts a `blob:` Worker that a CSP without `worker-src blob:` blocks. Tests: Vite+ (Vitest), PGlite, Playwright with axe, `write-excel-file` for XLSX test files.
- A library must not need Node modules that the browser or Workers lack (`nodemailer` and `pg` are the Node-only exceptions, see Cloudflare below), nor `eval` or `new Function`: the CSP has no `unsafe-eval`. zod therefore runs with `jitless` (`apps/web/src/zod-config.ts`, the first import of `router.tsx` and `start.ts`).
- Layout: `apps/web` (the app), `docker/`, `scripts/` (the two check scripts), `docs/superpowers/`.

## Conventions

- **Everything that is code is English:** identifiers (per the glossary), file names, URL paths, HTML ids, CSS classes, cookie names, test titles. Only visible text is translated.
- **Mail code** (`apps/web/src/mail/**`):
  - It runs in the browser (preview), on Workers and on Node. It has no server imports at runtime except the browser-safe `@/server/compare-code-points`, `@/server/media/ids`, `@/server/contacts/calendar`, `@/server/contacts/display-name` and `customFieldKey` from `@/server/contacts/fields`; everything else from `@/server` is a type import. No Node modules, no `eval` or `new Function`.
  - Placeholders in block templates work only in text, never in attributes, URLs or `<style>` (imported HTML may carry brand keys in `href`, `src` and CSS, see the Templates bullet). Brand values are put in when the mail is compiled (`compileMail`); contact values go into slots when it is filled (`fillMail`).
  - `{{unsubscribe.url}}` is the only key that is neither contact data nor a brand value. `compileMail(…, { unsubscribe: true })` gives it a required slot (the standard footer shows the link; imported HTML without the placeholder gets a line before `</body>`); with `false` the placeholder is refused (`invalid: 'unsubscribe'`). `fillMail` takes only an `http:` or `https:` address for it. Its value comes from the outbox only; `sendingValues` never gives it. The editor's preview and the sending build the source with the same `mailSourceOf` (`apps/web/src/mail/templates/mail-source.ts`).
  - A value is never parsed again: no value is read for placeholders or markers (`U+E000`/`U+E001`, which `stripMarkers` removes from every template text and brand value first). Values are escaped per context (`escapeHtml`, `cleanHeaderText`).
  - The lint override for `apps/web/src/mail/**/*.tsx` in the root `vite.config.ts` exists because mail components render once to an HTML string: inline styles are the only styling mail clients read, nothing re-renders, and the classes belong to the mail's own `<style>`, not to Tailwind. Do not copy it to other code.
  - Snapshots (`render.snapshot.test.tsx`) pin the HTML; update them only on purpose (`vp test -u`).
- **Templates** (`apps/web/src/server/templates/`, the editor in `apps/web/src/components/editor/`):
  - A template is stored only through `saveTemplate` (the checks of `save-checks.ts`, the usage of images in `template_media`, the choice of a global layout). Preview values come only from `previewValues`, which filters contact data by the user's access; values for sending only from `sendingValues` (`sending-values.ts`, by the area's field protection, no user), the source for sending from `templateMailSource`.
  - HTML enters only through `importHtml` (`apps/web/src/server/html-import/`), for templates and for layouts; never store or render HTML that did not pass it. An HTML file is decoded in the browser by `decodeHtmlBytes` (`apps/web/src/components/html-import/read-html-file.ts`, the HTML standard's encoding sniffing: byte order mark, a `<meta>` charset in the first 1024 bytes, else UTF-8 or, for invalid UTF-8, Windows-1252), never with `file.text()`; `importHtml` then declares UTF-8 in the HTML's `<meta>` elements, the encoding it is stored and sent in. In imported HTML a placeholder has its place by type: a URL brand key only as the whole `href` or `src` value and without a fallback, `unsubscribe.url` (`URL_SLOT_KEYS`) only as the whole `href` value and without a fallback, a colour or font brand key only inside CSS and without a fallback, none inside an Outlook conditional comment. `appOrigin` is a required parameter of the template functions that check links and images: pass the origin of the app's URL (`env.appUrl.origin`), never a default.
  - The XSS and bypass corpus (`apps/web/src/server/html-import/*.test.ts`, `bypass.test.ts`) is only ever extended: a fixed hole adds its vector, no case is removed or loosened.
  - Limits shared with forms (name and subject lengths) live in `server/templates/limits.ts`, a module without imports, so that browser code does not pull `save-checks.ts` and the HTML import with the caniemail data into its chunk.
- **Heavy browser libraries** (Tiptap, `read-excel-file`, `papaparse`, `fflate`) load only by dynamic `import()` in client code: the editor fields through `ClientOnly` with a placeholder of the same size (`text-block-editor.tsx` loads `text-block-field.tsx`, `inline-editor.tsx` loads `inline-field.tsx`, both through `LazyEditorField` in `lazy-editor-field.tsx`: an error boundary shows a failed load at the field with a button that loads it again, through `retryableLazy`, since React's `lazy` keeps a failed load failed), the import reader when a file is read. The dynamic import sits behind `import.meta.env.SSR` (the import reader: `import.meta.env.SSR && import.meta.env.PROD`, since the unit tests run with `SSR` and without `PROD`), which drops it from the server build; a static import of such a library, or of a module that statically imports it, from a route or component reaches the server bundle. The CI `build` job fails on a server bundle that contains one of them.
- **Images** are stored only through `storeImage` (`apps/web/src/server/media/media.ts`) and served only by `/media/<id>.<ext>` (`handleMediaRequest` in `media-request.ts`: 405 for other methods than GET and HEAD, an empty 503 with the image headers when the database or the storage fails); never write to a storage or link a storage URL directly. The storage packages (`s3mini`, `@vercel/blob`) load only behind `import.meta.env.VITE_VB_PLATFORM` and by dynamic import (`open-storage.ts`), and the CI bundle check covers them.
- **Attachments** (`apps/web/src/server/attachments/`) are stored only through `storeAttachment` (PDF, JPEG, PNG by signature, at most 5 files of 4 MiB per occasion without a wave; `send` in the area; an archived occasion takes none) and read through `readAttachments` (the wave preparer reads a wave's files once per run of the outbox and sender); the objects are private under `attachments/<id>` and never served. Without a wave an attachment is removed by the tick step `attachmentCleanup` after one day (`removeAttachment` removes it earlier); both go through `deleteFreeAttachment`, which locks the row (`for update`) in a transaction, checks that no wave holds it, deletes the object and then the row (a storage failure rolls back and keeps the row). `confirmWave` links the chosen files to the wave, taking only free ones of its occasion under the same row lock, so it waits for a deletion and then refuses the gone file; from then on they go with the wave (`attachments.wave_id`, cascade). The server functions are in `apps/web/src/functions/waves.ts`.
- **Content Security Policy:** every page gets the full policy with a nonce (`security-headers.ts`, the request middleware in `start.ts`); only `/media/*` and `/preview-frame` differ, and `/login/confirm` sends `Referrer-Policy: strict-origin` (its URL holds the login token; never `no-referrer`, which makes a POST's `Origin` `null` for the CSRF check). A new page needs no CSP work, but no inline script or style element without the nonce, and no `eval`. zod runs jitless (`zod-config.ts`).
- **E2E files** import `test` (and `expect`) from `apps/web/e2e/helpers/test.ts`, never from `@playwright/test`: it watches every browser context (also those opened with `browser.newContext()` in a `beforeAll`) and fails the test during which a page saw a CSP violation. The report arrives asynchronously; a test that provokes a violation on purpose waits for it with `cspViolationsReported(page)`. Playwright projects are `fundament`, `contacts`, `design` (the brand page and the sample mails; depends on `fundament`), `templates` (templates, editor, preview, image library, HTML import, layouts; depends on `contacts` and `design`) and `sending` (connection, sender, system sender, login link through Graph, disturbance, failed invitation, expiring secret; depends on `templates`; its first test sets the system sender, so every later mail goes through the fake provider). `runTick(app)` from `apps/web/e2e/helpers/tick.ts` runs a tick by hand (`POST /api/tick` with the `CRON_SECRET`), as the E2E server ticks only every 15 minutes.
- **New environment variables:** `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` (all or none, Node/Docker) and `BLOB_READ_WRITE_TOKEN` (Vercel); on Cloudflare the R2 binding `MEDIA_BUCKET`. `TEST_S3_URL` is for tests only. `docker/mailpit-relay.yaml` holds credentials and is never committed.
- **Imports** inside `apps/web/src` use the `@/` alias (it points to `apps/web/src`). No `../` imports (lint error); `./` in the same folder is fine.
- **UI text** lives only in `apps/web/src/i18n/de.ts` and `en.ts`. Every key exists in both. Read it with `useT()` in components and `translate(locale, key, params)` on the server. System mails use the recipient's language.
- **Page titles:** every route sets `head: (context) => pageHead(context, '<key>')` (`apps/web/src/i18n/page-title.ts`), which gives „{Seite} – Vereinsbote“ in the request's language and names the error or not-found page when the route fails. Admin pages use `adminPageHead` with a typed context.
- **Paths** used in code (`LOGIN_PATH`, `AFTER_SIGN_IN_PATH`) come from `apps/web/src/paths.ts`.
- **The page frame** (language, signed in or not, and for a signed-in user the navigation and the notice about the member data from `loadFrameInfo` in `apps/web/src/server/frame.ts`) comes from the root loader, once per document (`staleTime: Infinity`); client navigation does not ask again. Whatever changes the language or the session loads a new document: a redirect with `reloadDocument: true` (setup's sign-in, `requireRequestPrincipal`), `location.assign` or `location.reload` (Sign out, language switcher). The exception is a change of the navigation or the notices: a confirmed import, every save on the contact settings, and on the sending pages setting or removing the system sender, deleting it, saving a connection or a sender and the self test (they change the system-sender and disturbance notices) call `router.invalidate()`, which runs the root loader again. Protected pages and server functions still check the session themselves.
- **React Aria's `I18nProvider`** wraps the app once, in `apps/web/src/routes/__root.tsx`, with the request's language through `intlLocale` (`de-DE`, `en-US`), so React Aria's dates, numbers and own texts follow the page's language, not the browser's, also in the server render. Do not add local providers.
- **Notices for the next page** (a partner just deleted or created) go into the router's history state (`HistoryState` in `apps/web/src/router.tsx`), never into the URL; the page shows them once and removes them with `clearHistoryNotice` (`apps/web/src/components/contacts/history-notice.ts`).
- **Route files** named after a path parameter (`$contactId.tsx`) are exempt from `unicorn/filename-case` through an override in the root `vite.config.ts`.
- **Access levels** are defined once in `apps/web/src/server/permissions/levels.ts` (`accessLevels`); the schema and the level selects use that list.
- **Accessibility:** WCAG 2.2 AA.
  - Use React Aria Components. Show errors at the field. Announce changes in live regions.
  - Every page gets an axe check in E2E (`expectNoA11yViolations` in `apps/web/e2e/helpers/a11y.ts`) with no violations for `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa`.
- **Forms** use `PostForm` (`apps/web/src/components/post-form.tsx`): `method="post"` and a hydration gate, so a native submission never puts values into the URL. Submit buttons are `SubmitButton`.
- **Server functions** (`apps/web/src/functions/`):
  - They run behind the CSRF middleware (`apps/web/src/platform/csrf.ts`).
  - Expected refusals (a taken address, the last admin, a contact or area deleted in another tab) are returned as results, never thrown. Domain modules signal them with typed errors (for contacts in `apps/web/src/server/contacts/errors.ts`, e.g. `ContactNotFoundError`, `UnknownAreaError`), which the server function maps to a result (`CONTACT_GONE`, `{ ok: false, failure: 'gone' }`). Anything thrown reaches the browser only as a generic `ServerFunctionError` (`apps/web/src/platform/server-fn-errors.ts`, a function middleware in `start.ts`); redirects and not-found results pass.
  - A component waits for a `useServerFn` call with `settle` (`apps/web/src/components/settle.ts`): it gives `FAILED` when the call failed and `undefined` when the server redirected (the session ended). On `undefined` return without touching state.
  - An error thrown in a request middleware (`requestMiddleware` in `start.ts`) during a server-function request bypasses that function middleware: Start serializes it with its message to the browser. Request middleware must therefore only throw errors whose message is safe to show (or return a `Response`).
  - Start reads the whole body of a call with form data before the function runs. The request middleware `formBodyLimit` (`apps/web/src/platform/body-limit.ts`, after `csrf` in `start.ts`) answers such a call above 4.5 MB with 413 before the body is read, and one whose body breaks off with 400; it returns responses, never throws.
  - Each function authorizes itself from the session principal (`requireRequestPrincipal`), never from client input. A server function is reachable without its page.
  - Server modules are imported inside the handlers, so they stay out of the client bundle.
  - Validate input with zod.
- **Cloudflare:**
  - The database, the auth instance and the system mailer are request-scoped (`apps/web/src/platform/request-scope.ts`). Never cache an I/O object across requests.
  - The request's database ends with the response, so work after it (`platform.waitUntil`) must not use the database. The system mailer splits a mail for this: `prepare` does the database work inside the request, the delivery it returns renders the mail and calls the provider (login links, `createLinkSender`, which starts the delivery one macrotask after its callback has returned).
  - `nodemailer` and `pg` must never end up in the Cloudflare bundle. Load them only on the Node path, behind build-constant branches (`import.meta.env.VITE_VB_PLATFORM`). CI checks the bundle.
- **No secrets, e-mail addresses or tokens** in logs, URLs or error messages. Log error codes only, through `errorLabel` / `errorLabelWithCause` (`apps/web/src/server/error-label.ts`). Better Auth logs through the same labels (`logger` in `auth.ts`), and its HTTP errors go through `handleAuthRequest`, which logs a thrown error by code and a 5xx response by its status only.
- **Pages and responses:** `routerDefaults` (`apps/web/src/router-defaults.ts`) sets the generic, translated error and not-found pages; they never show an error's message. Every response gets the security headers of `apps/web/src/platform/security-headers.ts`: pages and API responses through the request middleware in `start.ts` (`securityHeadersFor`, a Content Security Policy with the request's nonce from `platform/csp-nonce.ts`; only `/preview-frame` and `/media/…` differ, and `/login/confirm` in its `Referrer-Policy`), the built assets under `/assets/` and the icons under `/social/` (served by Nitro, Vercel's CDN or Workers assets, never by Start) through `apps/web/src/platform/static-headers.ts` and `vite.config.ts`, with the base headers only. The router gets the same nonce through `createRouter({ ssr: { nonce } })`, set when it is created. Every E2E test fails on a CSP violation (`test` from `apps/web/e2e/helpers/test.ts`; import it instead of `@playwright/test`).
- **Work after the response** goes through `platform.waitUntil` (`createBackgroundRunner`): it never rejects into the runtime and warns once on Vercel or Cloudflare when the runtime offers no `waitUntil`.
- **Sending** (`apps/web/src/server/sending/`):
  - A mail goes to a provider only through a `Transport`, opened by `openSenderTransport` for a sender; never call Graph or Resend directly. The outbox (`outbox-step.ts`) and the system mailer are its only callers, and the self test of a sender.
  - Credentials are encrypted only with `encryptSecret(plaintext, key, secretAad('mail_connections', id, '<column>'))`, the column being `secret_ciphertext` or `webhook_secret_ciphertext`, and decrypted with the same associated data (`decryptSecret`), so a ciphertext copied to another row or column does not decrypt. A secret is never returned to the browser, logged or put in an error; a form field of a stored secret is empty and keeps it. A ciphertext that does not decrypt (e.g. after `APP_SECRET` changed) is a `SecretDecryptError`: the connection counts as disturbed.
  - `loadSender` (`senders.ts`) has no authorization: only the outbox (its wave preparer included) and the system mailer call it, never a server function with a client's id.
  - `SystemMailer.prepare(mail | null)` runs inside the request and does all the database work (system sender, credentials, brand, count), with the same statements whether or not a mail goes out; the delivery it returns runs one macrotask after the response (`createLinkSender`) and does not touch the database.
  - A quota refusal by the provider pauses the quota scope (a Graph sender, or a Resend connection) for at least an hour (ruling R5, `send_scope_pauses`); one entry then tests it.
  - The outbox backs off (`settle` in `outbox-step.ts`): an unclear send stops the connection for the run and pauses the scope for 15 minutes; a transient refusal stops the scope for the run and pauses it for the provider's `Retry-After`; a preparer that throws stops its sender for the run (the entry goes back to `planned` with one attempt). A new answer class needs its place there.
  - An outbox entry that is `uncertain` (it was `sending` for 10 minutes without an outcome) is **never sent again automatically**: only a person decides (`resendUncertain`, see Waves). The same holds for a send whose answer was unclear. Every retry of an entry keeps its Message-ID and its idempotency key (the entry id); the outbox sets both on the prepared mail, whatever the preparer hands. Resend keeps a key for 24 hours only (ruling R7, `Transport.idempotencyTrustedMs`): an entry whose first counted attempt (`first_attempt_at`) is more than 23 hours old goes out no more by itself; before preparing or sending it becomes `uncertain` (`outbox.keyExpired`, no request, no attempt; `keyOutlived` in `outbox.ts`), and a retry that would come after that becomes `uncertain` at once (`guardKeyLifetime`). Graph has no keys and is not limited so.
  - The outbox gets each mail from the preparer of the entry's source (`OutboxDeps.preparers`; `tick/steps.ts` sets the wave's `wavePreparer`). A preparer must be deterministic: the same entry and the same data give the same mail, because Resend refuses a retry whose payload differs from the one its key stands for. `EntryPreparer.startRun` gives a run a prepare function of its own that may keep what the run's entries share (the wave preparer keeps the setup and the files of one wave per sender, so a wave's attachments are read once per run, not per mail, while the senders' lanes take turns; at most one wave's files per sender). A stopped wave is decided where the outbox takes or plans an entry: `claimEntry` cancels instead of taking an entry of a stopped wave, and an entry that would wait again (retry, refused credentials, paused scope, spent subrequests) becomes `cancelled` instead of `planned`. Both read the wave's `stopped_at` under a share lock (`waveStopped`), after the entry's row lock; `stopWave` cancels the entries before it marks the wave, the same order, so they cannot deadlock.
  - **Cloudflare subrequests:** a Worker invocation allows 10,000 subrequests (Workers Paid). The outbox spends at most `CLOUDFLARE_PROVIDER_REQUESTS` (1,000) of them on the providers per invocation, through `TickContext.subrequests` (`apps/web/src/platform/subrequests.ts`): the cron handler hands one budget to every tick it chains (`runScheduledTicks`), `runTick` makes a fresh one per call otherwise. Provider requests go through `budgetedFetch`. A `fetch` the platform refused (`isSubrequestLimit`, "Too many subrequests") sent nothing: the adapters answer `transient` with `platform.subrequests`, never `uncertain`, and the outbox puts the entry back without an attempt and ends the run.
  - A disturbance names its reason by code (`disturbanceReason` in `disturbance.ts`): `credentials`, `mailbox` (`graph.mailbox`: Graph 403 or 404 on a mailbox after a token came) or `domain` (`resend.domain`: Resend 403 `validation_error`). A token decides only about `credentials`; the others are tested with one entry. `clearDisturbance(db, id, { code, since })` clears only the disturbance its caller read, so a run cannot clear one that another run recorded meanwhile.
  - The system mailer marks the system sender's connection disturbed when `send` is refused (credentials, mailbox, domain) or its secret does not decrypt; `sendingWarnings` first fetches a token for a Graph system sender (`checkSystemSender`). Removing the system mark goes through `clearSystemSender(db, actor, senderId)`, which refuses (`changed`) when that sender no longer holds it.
  - `kickOutbox` (the "sofort" run of 4b) must not use the request's database, which ends with the response on Cloudflare: the caller passes `kickRun`, a tick of the outbox step (`kickSteps`) with `KICK_BUDGET_MS` on a database of its own (`openOwnDb` in `platform/context.ts`, ended afterwards) and the invocation's subrequest budget (`invocationBudget`); it pings no heartbeat.
  - `DEV_PROVIDERS_URL` (the fake Graph and Resend, `vp run --filter web dev:providers`) is accepted only as an `http://localhost` origin with an `http://localhost` `APP_URL` and refused on Cloudflare and Vercel (`toDevProvidersUrl` in `env.ts`): credentials and mails would go unencrypted to it. Tests and development never use real provider accounts.
- **Unsubscribe links** (`apps/web/src/server/unsubscribe/`): the token (`token.ts`) holds the kind and key of every contact of the mail, the occasion and the area, sealed with AES-GCM (additional data `unsubscribe`) under keys derived from `APP_SECRET` (HKDF, `vereinsbote:unsubscribe:v1`) and written as base64url. It never expires and hangs on no outbox entry; its IV is an HMAC of the payload, so the same payload always gives the same token and a retried mail the same link. `openUnsubscribe` answers `null` for any token that does not open. `unsubscribeUrl` (`url.ts`) builds `${APP_URL}/unsubscribe/<token>` (`UNSUBSCRIBE_PATH`); the same link fills `{{unsubscribe.url}}` and the `List-Unsubscribe` header (with `List-Unsubscribe-Post: List-Unsubscribe=One-Click`), only in a wave with the link. A real token is never `test` (`TEST_UNSUBSCRIBE_PATH`).
- **Occasions** (`apps/web/src/server/occasions/`): an occasion belongs to one area and stands for a recurring kind of mail, each event a new wave. Reading needs `read` in the area, creating, changing and removing `edit`. Its template must belong to the area and its sender be released to it (`sender_areas`); `checkChoices` checks both inside the write's transaction, taking a `for share` lock on the sender row that `updateSender` and `deleteSender` also take, so a release cannot vanish in between. An occasion with waves is archived (`archived_at`), never deleted: it cannot be chosen or changed, and it keeps holding its template and sender (`TemplateInUseError` names the occasions, `SenderAreaInUseError` and `SenderInUseError('occasions')` refuse the sender side). `removeOccasion` locks the row, then counts its waves (`countWaves`); `confirmWave` holds the row (`for share`) while it makes a wave, so a removal waits and then archives. Its records carry `waves` and `lastWaveAt`. `limits.ts` is import-free so browser code can use `defaultUnsubscribe` and the name limit. Opt-outs of scope `occasion` hang on `contact_opt_outs.occasion_id` (cascade); tests that need one make a real occasion with `insertOccasion` (`server/occasions/testing.ts`), tests that need a wave insert its row with `insertWave` (`server/waves/testing.ts`).
- **Waves** (`apps/web/src/server/waves/`): `summarizeWave` and `confirmWave` need `send` in the occasion's area and refuse an archived occasion. `resolveRecipients` selects with the contact list's own conditions (`server/contacts/filters.ts`: kind, group, tag, the search over base fields; a single selection by ids only narrows them) and counts each excluded contact once, under its first reason (suppressed, exited, no address, address marked invalid in `contact_bounces` (`isEmailInvalid`), opt-out of the occasion, of its area). `planMails` (pure) plans one mail per contact (personal) or per address (circular, order of Design 11.2). The wave stores the template compiled at the confirmation (`compileMail(…, 'de', { unsubscribe })`) and its salutation texts. A compile problem (`compile`, `missingBrand`, `unsubscribe`), no recipients, attachments too large for a Graph sender (`graphRequestBytes` of a probe mail whose unsubscribe link in header and body has a stand-in token as long as the plan's longest, `standInUnsubscribeLink`) or a start in the past or more than a year ahead refuse it before any entry exists. One transaction holds the occasion (`for share`, version compared), inserts the wave (`request_id` unique with `on conflict do nothing`: a second confirmation of the same flow waits for the first and gets its wave), links the attachments, inserts the entries (`wave_id`, priority by kind) with their `wave_contacts`, and logs `wave.created` (`wave:<id>`, `{ occasionId, mails }`). The server function `confirmWave` kicks a wave sent at once (`kickRun`). Before each mail `wavePreparer` (`preparer.ts`) checks the entry's contacts again (`contactsWithMarks`, `exclusionOf`, or `deleted`; today by `todayInClubZone`): a personal mail goes to the contact's current address; a circular entry belongs to its address, so a contact with another address drops out and the next moves up (none left: `skip`, with the first contact's reason, e.g. `addressChanged`). The first contact left fills the compiled mail through `sendingValues`; a missing required value fails the entry as `missing:<key>`, a file gone from the storage as `attachmentMissing`. Skip and failure codes name a reason or a key, never a value or an address. `stopWave` and `resendUncertain` (`stop.ts`) need `send` in the wave's area: a stop cancels every planned entry, then records `stopped_at` and who stopped (a second stop changes and logs nothing; `wave.stopped` with `{ cancelled }`); `resendUncertain` moves only an `uncertain` entry of a wave that was not stopped back to `planned`, with its id (Message-ID and idempotency key stay), clears `digested_at` and logs `wave.entry_resent` (`wave:<id>`, `{ entryId }`). Their refusals (`WaveNotFoundError`, `WaveEntryNotFoundError`, `WaveEntryStateError`) become results in `failures.ts`; the server functions are in `functions/waves.ts`. The schema modules `waves.ts`, `sending.ts` and `occasions.ts` import each other for lazy `references(() => …)` only: never use another schema module's value while one loads.
- **System mails** (login links, invitations, warnings) go only through `createSystemMailer` (`apps/web/src/server/mail/system-mailer.ts`, a facade on `server/sending/system-mailer.ts`): through the system sender's transport without the outbox (`kind: 'system'`), counted against its daily limit, else through `DEV_SMTP_URL` on the Node path, else `MailerNotConfiguredError`. Their content is a `SystemMailContent` (heading, paragraphs, a button with a finished URL) from the `mail.system.*` texts; `composeSystemMail` renders it in the CD's standard layout and falls back to a plain version (also for an `http:` link of a local `APP_URL`, which blocks refuse). A login link request runs the same statements in the same order for every address (the window and the day's count in `allowLoginLink`, where `skipLoginLinkOfDay` counts nothing; the user lookup; `prepare(null)`, which counts nothing), so neither its result nor its time tells whether the address is invited; `auth.test.ts` compares the statements through `createTestDb({ logQuery })`.
- **Login links** lead to the confirmation page `/login/confirm?token=…` (`LOGIN_CONFIRM_PATH`, `routes/login_.confirm.tsx`); only its POST (`confirmLoginLink` → `verifyLoginLink`) uses up the token, so a mail scanner's GET does not. Better Auth's `GET /api/auth/magic-link/verify` is in `DISABLED_PATHS`; never link to it. Limits per address (HMAC, `login-link-days.ts`): one link per minute and `LOGIN_LINKS_PER_DAY` (10) per club day. A resend of an invitation goes through `resendInvitation` (admin, status `invited`, at most once a minute, logged as `user.invitation_resent`).
- E-mail addresses are stored and compared through `normalizeEmail` (trim and lowercase).
- **Contacts** (`apps/web/src/server/contacts/`):
  - Contact data leaves the server only through functions that filter by `loadContactAccess` (`access.ts`): protected fields the user may not see are not delivered, not just hidden, and search and filters cover them only for users who see them. The admin role alone gives no access.
  - Never call `loadContactAccess` inside a transaction: it runs queries in parallel, which pg warns about on one client. Load the access first, then open the transaction.
  - A write that changes contacts, suppressions or opt-outs takes the import-state lock of the kind (`lockImportState`, `import-state.ts`) before it changes anything, so it waits for a running import of that kind and cannot deadlock with it. It bumps the stock version, so a preview made before it cannot be confirmed.
  - Search terms and filter values go by POST, never into a URL; the URL of the contact list carries only `kind`. The list route sets `gcTime: 0`: the list keeps its first page as its own state, so every visit loads it anew instead of showing a cached page.
  - The import sends the mapped columns only (of discarded ones just the header, for the remembered mapping) as gzip-compressed JSON in `FormData` (`encodeImportPayload` / `decodeImportPayload`); the limits (10,000 rows, 4,000,000 bytes compressed, 16 MiB unpacked) are in `import/payload.ts`. The file itself is read in the browser and never sent.
  - "Today" (the import day, a reached exit date) is `todayInClubZone` (`calendar.ts`, `Europe/Berlin`), never the server's or the browser's day. Date fields are calendar dates (`YYYY-MM-DD`, Postgres `date`).
  - Suppressions and opt-outs hang on `contact_key` (`nr:<number>`, for a partner without customer number `email:<address>`), not on the contact, so they survive every import. When a partner's key changes they follow it (`rekeyContactKey`), or are copied when another partner keeps the old key (`copyContactKey`). Partners without number that share an address therefore share them, also when an edit moves one onto the other's address.
  - The activity log names a contact by number or id (`member:<nr>`, `partner:<nr>`, `contact:<uuid>`, `auditTarget`), never by name or address.
- `DEV_SMTP_URL` (`apps/web/src/server/mail/smtp-transport.ts`) sends unencrypted only to the local machine; any other host must offer STARTTLS. No credentials in workflows either: the CI PostgreSQL services use trust authentication.
- Credentials are encrypted with AES-GCM through WebCrypto only, so the code runs on Node and on Workers.
- **Tick steps** go into `apps/web/src/server/tick/steps.ts` and respect the tick's time budget. A step resumes at the next tick. The order is `pruneAuthRecords`, `outbox`, `staleImportWarning`, `sendingWarnings`.
- **Warning mails** (`staleImportWarning`, `sendingWarnings` in `apps/web/src/server/sending/warnings.ts`) claim their marker in `system_state` first, then send to every active admin in their language, then write the activity log. When the log entry fails the marker is given back and the error goes on, so the next tick warns again. The sending warnings are the Graph secret (stages 30, 14, 7 and 1 day, each once), a disturbed connection (once per disturbance) and one digest per club day of new failed or unclear outbox entries. A warning that reached nobody gives its claim back and is tried again after an hour (`WARNING_RETRY_MS`, also for `staleImportWarning`), without a log entry. They name connections, senders and numbers, never a recipient or a secret. The admin overview (`sendingOverview`) and the page frame (`sendingNotice`) show the same state.
- Migrations run automatically on deploy and must stay compatible with older data. On Vercel they run in production builds only, in preview builds only with `MIGRATE_ON_PREVIEW=1` (`db:migrate:vercel`); a Vercel build (`VERCEL=1` or the marker `VB_VERCEL_BUILD=1` that `apps/web/vercel.json` sets) without a known `VERCEL_ENV` fails instead of skipping them.

## Testing

- **TDD:** write the failing test first, see it fail, then implement.
- Unit tests sit next to the code (`*.test.ts`, `*.test.tsx`). Database tests use PGlite through `createTestDb()` (`apps/web/src/server/db/test-db.ts`), a fresh migrated in-memory database per call that closes when the calling test ends. Call it inside a test, not in `beforeAll`: an open PGlite holds its memory until garbage collection, and unclosed ones let the test workers grow by gigabytes. `createTestDb({ logQuery })` hands the SQL of every statement to a callback, for tests that compare the statements of two calls.
- Each database test starts its own PGlite instance, which is slow on CI runners with coverage; the test and hook timeouts are therefore 30 s (`apps/web/vite.config.ts`). Do not lower them.
- PGlite runs one statement at a time, so it cannot show races. Tests that need real concurrency are `*.postgres.test.ts`, run against PostgreSQL when `TEST_POSTGRES_URL` is set (CI sets it), create and drop a database of their own, and are skipped otherwise (`describe.skipIf`, with the reason in the title).
- E2E tests are Playwright files named `*.e2e.ts` in `apps/web/e2e/`. They run against the Node build on port 3100 with the fixed values in `apps/web/e2e/env.ts`.
- Every E2E file belongs to a Playwright project of its own in `apps/web/playwright.config.ts` (`fundament`, `contacts`, `design`, `templates`, `sending`); a file without one does not run. A file that builds on another file's data names that project in `dependencies`, as `contacts` and `design` do with `fundament`, `templates` with `contacts` and `design` and `sending` with `templates`. They open the admin's pages with the session `fundament` saves at its end (`newAdminContext`, `apps/web/e2e/helpers/admin-session.ts`) instead of signing in again: the server sends one sign-in link per address and minute, and ten per day. `signIn` (`apps/web/e2e/helpers/sign-in.ts`) follows the link to the confirmation page and presses „Anmelden“.
- **Test data is always invented** (made-up names, addresses at `example.org` or a `.test`/`.example` domain). A club's real exports never go into the repository, not even shortened. Import files for tests are built in the test: XLSX with `write-excel-file`, CSV and HTML as text (e.g. encoded as Windows-1252 in the test); no binary fixtures.

## Security and supply chain

- GitHub Actions are pinned by the full commit SHA with the version as a comment: `uses: owner/action@<sha> # vX.Y.Z`. Never a tag or branch.
- Container images are pinned by digest (`image:tag@sha256:…`) in the Dockerfile, both Compose files (including Neon's `wsproxy` behind the Compose profile `cloudflare`) and the CI services.
- Vulnerabilities are reported privately (`SECURITY.md`).
- `pnpm cve` (cve-lite) scans `pnpm-lock.yaml` and fails on high or critical advisories. It runs in the `pre-push` hook and in the CI `check` job. It knows only OSV and npm advisories; Snyk (GitHub integration, PR check) uses its own database and can report more. Fix a finding by updating, or with a scoped `overrides` entry like the esbuild one. Snyk findings without a fixed version go into `.snyk`, each with a reason and an expiry date.
- SonarQube Cloud analyzes in CI (`sonar-project.properties`, step in the `test` job, coverage from `vp test --coverage`). Automatic Analysis stays off. The quality gate wants 80 % coverage on new code from the unit tests; only framework- or runtime-bound code tested by E2E (routes, `*.tsx` components, server functions, router, entry points, migration CLIs, `sample-cli.ts`) is excluded, so new logic in plain modules needs unit tests. The dictionaries `i18n/de.ts` and `i18n/en.ts` are excluded from the duplication check (`sonar.cpd.exclusions`). Sort strings with a compare function (`compareCodePoints`) and avoid regexes that can backtrack super-linearly.
- Renovate (`.github/renovate.json`) maintains the SHA, digest and catalog pins. Do not edit pins by hand without a reason. No `renovate.json` at the root: Renovate would read it instead.
- CI runs with least privilege: `permissions: contents: read`, `persist-credentials: false`, no `pull_request_target`. The one exception is `.github/workflows/release.yml` (persisted checkout credentials for authenticated tag lookups; runs on `main` only): do not "fix" it. Its `GITHUB_TOKEN` is read-only too; it pushes, tags and opens the release pull request with an installation token of the GitHub App `mheob-helper` (`vars.BOT_CLIENT_ID`, `secrets.BOT_PRIVATE_KEY`, limited to `contents: write` and `pull-requests: write`), never with a personal access token.
- `pnpm-workspace.yaml` sets `minimumReleaseAge`, `trustPolicy: no-downgrade`, `strictDepBuilds` with `allowBuilds`, and `blockExoticSubdeps`. Do not weaken them. A new install script needs an entry in `allowBuilds` and a reason.
- A vulnerable transitive version is lifted with a scoped override in `pnpm-workspace.yaml` (prefer a parent-scoped key such as `"@esbuild-kit/core-utils>esbuild"`, a version range in the key also works; `"catalog:"` as the value; a comment with the advisory). Remove it once the dependency ships a fixed version.
- Containers run as a non-root user without dev dependencies.

## Releases

- Releases use Changesets (`.changeset/`). Only `web` (`apps/web`) is versioned; the root package is not, and nothing goes to npm.
- **Every user-facing change gets a changeset** (`pnpm changeset`, text in English, `patch` fix, `minor` feature, `major` breaking). Docs, tests, CI and dependency updates need none (`pnpm changeset --empty` if the `pre-push` hook asks).
- Never edit `apps/web/package.json`'s `version` or `apps/web/CHANGELOG.md` by hand and never run `changeset version` in a branch: the release pull request ("chore(release): version packages", `.github/workflows/release.yml`) does it. `vp fmt` ignores `CHANGELOG.md`.
- The release pull request needs a code owner's approval before Kodiak merges it; that approval is the release gate. The release workflow opens it as the GitHub App `mheob-helper`. Never open it with the owner's token (the owner's own pull requests bypass review).
- The `pre-push` hook (`.vite-hooks/pre-push`) runs `changeset status --since=origin/main`; it is skipped when `CI` is set.

## Commits

- Conventional Commits per `@mheob/commitlint-config`: lowercase type, optional scope, description at most 50 characters, starting lowercase, no period at the end, header at most 72 characters. Example: `feat(areas): rename an area`.
- `pnpm commit` starts czg. The Git hooks come from Vite+ (`.vite-hooks/`): `pre-commit` runs `vp staged`, `commit-msg` runs commitlint. Never skip them.
- If `.git/gitbutler` exists, GitButler manages the checkout. Commit with the `but` CLI, not with `git add` or `git commit` (see the `but` skill if available).
- Pull requests are squash-merged with the PR title and description as the commit message. Put `Closes #123` in the PR description.

## Keeping the docs current

Any change that affects commands, setup, conventions, architecture or operations must update `README.md`, `AGENTS.md` and `CONTRIBUTING.md` in the same change. The spec and the plans live in `docs/superpowers/`; `vp fmt` ignores that folder on purpose.
